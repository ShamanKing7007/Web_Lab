# Подготовка к защите лабораторной работы N5

## Сверка с требованиями Lab5.md

Проект в целом соответствует требованиям лабораторной по Redis с учетом уточнения, что вместо `items` используются `notes`.

Что реализовано:

- Redis добавлен в `deploy/docker-compose.yml` как сервис `redis` на образе `redis:7-alpine`.
- Redis защищен паролем через `redis-server --requirepass ${REDIS_PASSWORD}`.
- Для Redis включена персистентность `--appendonly yes`.
- Приложение получает настройки Redis из переменных окружения: `REDIS_HOST`, `REDIS_PORT`, `REDIS_PASSWORD`, `REDIS_DB`, `CACHE_TTL_DEFAULT`.
- Выделен отдельный слой кеша `internal/cache`, где находятся методы `Get`, `Set`, `Del`, `DelByPattern`.
- Для хранения объектов используется JSON-сериализация.
- Все ключи создаются с префиксом `wp:`.
- Все ключи, которые записываются в Redis, имеют TTL.
- `GET /auth/whoami` кеширует публичный профиль пользователя.
- `GET /notes?page=1&limit=10` кеширует список заметок текущего пользователя с учетом пагинации.
- `GET /notes/:id` кеширует конкретную заметку текущего пользователя.
- `POST /notes` удаляет кеш списков заметок текущего пользователя.
- `PUT /notes/:id`, `PATCH /notes/:id`, `DELETE /notes/:id` удаляют кеш конкретной заметки и кеш списков заметок.
- Access JWT получает `jti`, а Redis хранит только JTI, а не полный access token.
- `/auth/logout` удаляет JTI текущей access-сессии и кеш профиля.
- `/auth/logout-all` удаляет все access-JTI пользователя по паттерну и кеш профиля.
- Пароли, соли, refresh token и полные access token не сохраняются в Redis.
- Если Redis недоступен при старте, приложение не падает, а отключает кеш.

Итог по соответствию:

- Исходное требование про `items` адаптировано к текущему проекту как `notes`.
- Кеширование списков реализовано для `GET /notes?page={page}&limit={limit}`.
- Кеширование конкретного элемента дополнительно реализовано для `GET /notes/:id`.
- Требования по Redis, TTL, префиксам, JTI и инвалидации выполнены.

## Контрольные вопросы из ТЗ

### 1. В чем разница между стратегиями Cache-Aside и Write-Through?

Cache-Aside означает, что приложение само управляет кешем. При чтении оно сначала смотрит в Redis. Если данных нет, приложение идет в базу данных, получает данные, кладет их в кеш и возвращает клиенту. При изменении данных приложение обычно удаляет устаревший ключ из кеша.

Write-Through означает, что запись одновременно проходит через кеш и основное хранилище. То есть при изменении данных кеш обновляется сразу вместе с базой. Плюс Write-Through в том, что кеш чаще остается актуальным. Минус в том, что запись становится сложнее и потенциально медленнее.

В проекте используется Cache-Aside: `GET /notes?page&limit`, `GET /notes/:id` и `/auth/whoami` сначала проверяют Redis, а при промахе читают из PostgreSQL и записывают результат в Redis.

### 2. Что такое Thundering Herd problem и как кеширование может помочь или усугубить ее?

Thundering Herd problem возникает, когда много клиентов одновременно запрашивают одни и те же данные, а кеш в этот момент пустой или ключ только что истек. Все запросы одновременно идут в базу данных, из-за чего база получает резкий всплеск нагрузки.

Кеширование помогает, если ключ уже есть в Redis: повторные запросы не доходят до базы. Но кеширование может усугубить проблему, если популярный ключ одновременно истекает для всех клиентов.

Чтобы снизить риск, можно использовать разные TTL с небольшим случайным разбросом, блокировку на пересборку кеша, предварительное обновление популярных ключей или singleflight-подход, когда только один запрос пересобирает кеш, а остальные ждут результат.

### 3. Почему не рекомендуется использовать команду KEYS * в продакшене на больших объемах данных?

`KEYS *` проходит по всему пространству ключей Redis и может заблокировать сервер на время выполнения. Если ключей много, Redis перестает быстро отвечать на обычные запросы.

В продакшене лучше использовать `SCAN`, потому что он обходит ключи постепенно и не блокирует Redis на длительное время. В проекте массовое удаление реализовано через `SCAN + UNLINK` в методе `DelByPattern`.

### 4. Как обеспечить согласованность данных между БД и кешем при одновременной записи?

Основной источник истины должен быть один, обычно это база данных. Безопасный подход: сначала успешно изменить данные в PostgreSQL, затем удалить или обновить соответствующий ключ в Redis. Если кеш удалить до записи в БД, другой запрос может успеть прочитать старые данные из БД и снова положить их в кеш.

В проекте используется инвалидация после успешного изменения в БД. Например, при `PUT/PATCH/DELETE /notes/:id` сначала обновляется или удаляется запись в PostgreSQL, затем удаляется ключ конкретной заметки `wp:notes:user:{userId}:detail:{noteId}` и ключи списков `wp:notes:user:{userId}:list:*`.

### 5. Зачем нужен TTL у ключей кеша, если мы реализуем инвалидацию при записи?

TTL нужен как страховка. Инвалидация может не сработать из-за ошибки сети, падения Redis, бага в коде или непредвиденного сценария изменения данных. TTL гарантирует, что даже забытый или устаревший ключ не будет жить бесконечно.

Также TTL ограничивает потребление памяти Redis. В проекте TTL задается через `CACHE_TTL_DEFAULT`, а для access-JTI равен времени жизни access token.

### 6. Почему хранение JTI Access токена в Redis позволяет реализовать мгновенный Logout, несмотря на Stateless природу JWT?

Обычный JWT является stateless: если подпись валидна и срок действия не истек, сервер принимает токен без обращения к хранилищу. Поэтому без дополнительного состояния logout не может мгновенно отозвать уже выданный JWT.

JTI превращает access token в проверяемую сессию. При логине сервер записывает в Redis ключ `wp:auth:user:{userId}:access:{jti}`. При каждом защищенном запросе сервер проверяет не только подпись JWT, но и наличие этого JTI в Redis. При logout ключ удаляется, и тот же JWT сразу перестает проходить проверку.

### 7. Какие данные из лабораторной работы N3 безопасно кешировать, а какие нет?

Безопасно кешировать:

- JTI access token, потому что это идентификатор, а не полный токен.
- Публичный профиль пользователя без пароля, соли и reset token.
- Технический статус сессии, например строку `valid`.
- Идентификаторы сущностей, если они не раскрывают секреты.

Нельзя кешировать:

- Пароли.
- Хеши паролей и соли.
- Полные access token.
- Полные refresh token.
- Reset token в открытом виде.
- OAuth access token провайдера, если он не нужен для текущей задачи и не защищен дополнительно.

В проекте Redis хранит только `UserResponse`, данные заметки и JTI access-сессии.

### 8. Как повлияет перезапуск контейнера Redis на работу приложения?

Если включена персистентность AOF или RDB, Redis после перезапуска восстановит часть или все данные с диска. В проекте включено `--appendonly yes`, поэтому Redis пишет операции в AOF и может восстановить ключи после рестарта.

Если персистентности нет, после перезапуска Redis станет пустым. Тогда кеш профилей и заметок просто пересоздастся при следующих запросах. Для access-JTI последствия важнее: если все JTI потеряются, уже выданные access token могут перестать проходить проверку, если приложение требует наличие JTI. В текущей реализации при доступном Redis отсутствие JTI означает `401`.

### 9. Что такое сериализация и зачем она нужна при сохранении объектов в Redis?

Сериализация — это преобразование объекта из памяти программы в формат, который можно сохранить или передать. Redis хранит строки, байты и структуры данных, но Go-структуру напрямую туда положить нельзя.

В проекте используется JSON. Например, `NoteResponse` или `UserResponse` превращается в JSON-строку, сохраняется в Redis, а при чтении обратно преобразуется в Go-структуру.

### 10. Как префиксы ключей помогают в управлении кешем?

Префиксы делают ключи понятными и предотвращают конфликты имен. По ключу сразу видно, к какой части приложения он относится.

Примеры из проекта:

- `wp:users:profile:{userId}` — кеш профиля пользователя.
- `wp:notes:user:{userId}:list:page:{page}:limit:{limit}` — кеш списка заметок пользователя с учетом пагинации.
- `wp:notes:user:{userId}:detail:{noteId}` — кеш конкретной заметки пользователя.
- `wp:auth:user:{userId}:access:{jti}` — access-сессия пользователя.

Префиксы также позволяют удалять группы ключей по паттерну, например все access-JTI пользователя через `wp:auth:user:{userId}:access:*`.

### 11. Зачем необходимо защищать Redis паролем даже внутри закрытой Docker сети?

Docker-сеть снижает риск внешнего доступа, но не заменяет аутентификацию. Внутри одной сети могут находиться другие контейнеры, и при ошибке конфигурации Redis может стать доступен шире, чем планировалось.

Пароль добавляет отдельный слой защиты. Если какой-то контейнер или процесс получит сетевой доступ к Redis, ему все равно нужен пароль. В проекте пароль задается через `REDIS_PASSWORD` и используется в `docker-compose.yml` и Go-клиенте.

## Дополнительные вопросы по теории

### Почему Redis часто быстрее PostgreSQL для кеша?

Redis хранит данные в памяти и работает как key-value хранилище. Для получения значения по ключу ему не нужно выполнять SQL-запрос, строить план запроса, читать индексы и строки таблиц. Поэтому Redis хорошо подходит для часто читаемых готовых ответов API.

### Почему Redis не заменяет PostgreSQL?

Redis в этой работе используется как кеш и хранилище сессий, а PostgreSQL остается основным источником истины. В PostgreSQL есть транзакции, связи, ограничения, надежное хранение бизнес-данных и удобные запросы. Redis ускоряет доступ, но не должен быть единственным местом хранения заметок или пользователей.

### Что такое cache hit и cache miss?

Cache hit — данные найдены в Redis, и приложение возвращает их без запроса в PostgreSQL.

Cache miss — данных в Redis нет, поэтому приложение идет в PostgreSQL, получает данные, записывает их в Redis и возвращает клиенту.

### Почему при изменении данных чаще удаляют ключ, а не обновляют его?

Удаление проще и безопаснее. Если удалить ключ, следующий GET сам пересоздаст кеш из актуальной базы. При ручном обновлении кеша можно ошибиться в формате, забыть часть связанных ключей или записать данные, которые еще не зафиксированы в БД.

### Что такое TTL?

TTL — время жизни ключа. Когда TTL истекает, Redis автоматически удаляет ключ. В проекте TTL для обычного кеша задается через `CACHE_TTL_DEFAULT`, а TTL access-JTI равен `JWT_ACCESS_EXPIRATION`.

### Чем DEL отличается от UNLINK?

`DEL` удаляет ключ синхронно и может занять время, если значение большое. `UNLINK` отвязывает ключ и удаляет память асинхронно, поэтому лучше подходит для массовой инвалидации. В проекте `DelByPattern` использует `UNLINK`.

### Почему для удаления по паттерну в коде используется SCAN, а не KEYS?

`SCAN` обходит ключи постепенно и не блокирует Redis надолго. `KEYS` удобен для ручной проверки на маленькой базе, но в продакшене может создать задержки.

### Что будет, если Redis переполнится по памяти?

Поведение зависит от настройки `maxmemory-policy`. Redis может начать удалять ключи по политике вытеснения или возвращать ошибки записи. Для кеша это допустимо, если приложение умеет работать без кеша. Для сессий это критичнее, поэтому в реальном продакшене память и eviction policy нужно настраивать отдельно.

### Почему нельзя хранить полный access token в Redis?

Полный access token позволяет обращаться к API от имени пользователя до истечения срока действия. Если Redis будет скомпрометирован, злоумышленник сможет использовать эти токены. JTI сам по себе не дает доступа, потому что для запроса все равно нужен подписанный JWT.

### Что такое JTI?

JTI — JWT ID, уникальный идентификатор конкретного JWT. В проекте он генерируется через `uuid.NewString()` и записывается в стандартное поле `RegisteredClaims.ID`.

## Дополнительные вопросы по моей реализации

### Где в проекте находится Redis-клиент?

Redis-клиент инкапсулирован в пакете `internal/cache`. Основной тип — `cache.Service`. Он создает `go-redis` клиент, проверяет подключение через `PING` и предоставляет методы `Get`, `Set`, `Del`, `DelByPattern`.

### Почему выбран go-redis?

`go-redis/v9` — низкоуровневый Redis-клиент для Go. Он разрешен требованиями лабораторной, потому что не делает автоматическое кеширование на уровне роутинга, а только дает команды Redis. Логика ключей, TTL и инвалидации явно написана в сервисном слое.

### Какие ключи создает приложение?

Основные ключи:

```text
wp:auth:user:{userId}:access:{jti}
wp:users:profile:{userId}
wp:notes:user:{userId}:list:page:{page}:limit:{limit}
wp:notes:user:{userId}:detail:{noteId}
```

Все они имеют префикс `wp:` и TTL.

### Что хранится в ключе access-сессии?

В ключе `wp:auth:user:{userId}:access:{jti}` хранится строка `"valid"`. Полный access token в Redis не сохраняется.

### Как приложение проверяет access token?

Сначала JWT парсится и проверяется по подписи и сроку действия. Потом из claims берутся `user_id` и `jti`. После этого приложение проверяет наличие ключа `wp:auth:user:{userId}:access:{jti}` в Redis. Если Redis доступен, но ключа нет, запрос получает `401`.

### Как работает logout?

`/auth/logout` получает access token из cookie, парсит его, достает JTI и удаляет ключ `wp:auth:user:{userId}:access:{jti}` из Redis. Также удаляется кеш профиля `wp:users:profile:{userId}`. Refresh token дополнительно отзывается в PostgreSQL.

### Как работает logout-all?

`/auth/logout-all` отзывает все refresh token пользователя в PostgreSQL, затем удаляет все access-JTI пользователя из Redis по паттерну `wp:auth:user:{userId}:access:*` и очищает кеш профиля.

### Почему кеш заметки включает userId?

Ключ заметки имеет вид `wp:notes:user:{userId}:detail:{noteId}`. Это защищает от ситуации, когда два пользователя обращаются к одному `noteId` или злоумышленник знает UUID чужой заметки. Кеш привязан не только к заметке, но и к владельцу запроса.

### Почему профиль пользователя кешируется как UserResponse?

`UserResponse` содержит только публичные поля: `id`, `email`, `created_at`, `updated_at`. В нем нет `password_hash`, `salt`, reset token и OAuth-секретов. Это соответствует требованию не хранить чувствительные данные в кеше.

### Как кешируется список /notes?

Список кешируется в `NoteService.GetAll`. После валидации пагинации формируется ключ `wp:notes:user:{userId}:list:page:{page}:limit:{limit}`. Если ключ есть в Redis, приложение возвращает готовый `NotesResponse`. Если ключа нет, приложение читает список из PostgreSQL, формирует ответ с `data` и `meta`, сохраняет его в Redis с TTL и возвращает клиенту.

### Почему ключ списка включает userId, page и limit?

`userId` нужен, чтобы списки разных пользователей не смешивались. `page` и `limit` нужны, потому что разные параметры пагинации дают разные наборы заметок. Без этих параметров приложение могло бы вернуть не ту страницу или не тот размер списка.

### Как инвалидируется кеш списка?

При `POST /notes` удаляются все ключи списков текущего пользователя по паттерну `wp:notes:user:{userId}:list:*`. При `PUT/PATCH/DELETE /notes/:id` удаляется и кеш конкретной заметки, и кеш всех списков пользователя, потому что измененная заметка может находиться на любой странице.

### Что произойдет, если Redis недоступен при старте приложения?

`cache.NewService` делает `PING` с таймаутом. Если Redis не отвечает, приложение логирует ошибку и запускается с выключенным кешем. Методы `Get`, `Set`, `Del`, `DelByPattern` в этом режиме ничего не делают и не ломают приложение.

### Почему это одновременно плюс и компромисс?

Плюс: приложение не падает из-за временной недоступности Redis, CRUD и авторизация продолжают работать.

Компромисс: если Redis недоступен, механизм мгновенного отзыва access token через JTI временно не работает как строгий серверный реестр сессий. Для учебной работы это соответствует требованию, что кеш должен быть опциональным. В продакшене для высокой безопасности можно выбрать fail-closed поведение: если Redis недоступен, запрещать защищенные запросы.

### Как проверить, что кеш реально работает?

1. Запустить проект:

```powershell
cd deploy
docker compose up -d --build
```

2. Выполнить login и `/auth/whoami`.

3. В RedisInsight или Redis CLI найти ключи:

```text
wp:auth:user:*:access:*
wp:users:profile:*
```

4. Выполнить `GET /notes?page=1&limit=10`.

5. Найти ключ:

```text
wp:notes:user:*:list:page:1:limit:10
```

6. Выполнить `GET /notes/:id`.

7. Найти ключ:

```text
wp:notes:user:*:detail:*
```

8. Выполнить `PATCH /notes/:id` или `DELETE /notes/:id` и убедиться, что ключ заметки и ключи списков удалились.

### Как проверить TTL?

Через Redis CLI:

```bash
docker exec web_labs_redis redis-cli --pass redis_secure_password_change_in_prod TTL wp:users:profile:{userId}
```

Если Redis возвращает положительное число, значит у ключа есть TTL. Если `-1`, TTL отсутствует. Если `-2`, ключ не существует.

### Почему в RedisInsight могут не отображаться ключи?

Возможные причины:

- Приложение еще не выполнило запросы, которые создают кеш.
- Контейнер `app` не был пересобран после изменения кода.
- Ключи истекли по TTL.
- В фильтре RedisInsight указан неправильный паттерн.
- Подключение открыто к другой logical database.

В проекте нужно смотреть `db0` и фильтр `wp:*`.

### Почему access-JTI может быстро исчезать?

TTL access-JTI равен `JWT_ACCESS_EXPIRATION`. Если в `.env` стоит `JWT_ACCESS_EXPIRATION=30s`, ключ исчезнет примерно через 30 секунд. Для демонстрации удобно поставить `15m`.

### Почему refresh token остался в PostgreSQL?

В лабораторной N3 refresh token уже хранился в БД. В текущей реализации это сохранено: refresh token хешируется и хранится в PostgreSQL, а Redis используется для access-JTI. Это разделяет долгоживущие refresh-сессии и короткоживущие access-сессии.

### Какие данные можно показать преподавателю в RedisInsight?

Можно показать:

- Ключи `wp:*`.
- TTL ключей.
- Значение access-JTI `"valid"`.
- JSON профиля пользователя.
- JSON заметки.

Не нужно показывать `.env` целиком, потому что там есть секреты: пароли БД, JWT-секреты и OAuth credentials.
