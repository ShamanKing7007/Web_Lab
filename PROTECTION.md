# Защита проекта Web_Labs

## Что это за проект

`Web_Labs` — RESTful API для заметок с модулем аутентификации и авторизации.

Технологии:
- Go 1.26
- Gin
- GORM
- PostgreSQL 16
- Docker Compose

Функциональность проекта закрывает две части:
- ЛР 2: CRUD для заметок, soft delete, пагинация, модульная структура
- ЛР 3: регистрация, логин, JWT, refresh flow, cookies, OAuth 2.0, защита ресурсов

## Архитектура

Проект построен по слоям:
- `handler` — HTTP-обработчики
- `service` — бизнес-логика
- `repository` — работа с БД
- `models` — GORM-модели
- `middleware` — проверка access token

Ключевые модули:
- `internal/notes` — заметки
- `internal/users` — пользователи, сессии, JWT, OAuth, password reset

## Что реализовано в проекте

### 1. CRUD заметок

Маршруты:
- `GET /notes`
- `GET /notes/:id`
- `POST /notes`
- `PUT /notes/:id`
- `PATCH /notes/:id`
- `DELETE /notes/:id`

Особенности:
- заметки принадлежат конкретному пользователю
- чужую заметку нельзя читать, менять или удалять
- удаление сделано через `DeletedAt` и GORM soft delete
- список заметок поддерживает `page` и `limit`

### 2. Регистрация и логин

Маршруты:
- `POST /auth/register`
- `POST /auth/login`

Как это работает:
- при регистрации пароль не хранится в открытом виде
- для каждого пользователя генерируется своя соль
- пароль хешируется через `bcrypt(salt + password)`
- при логине создаются `access token` и `refresh token`

### 3. JWT и cookies

В проекте используются два токена:
- `access token` — короткоживущий JWT для доступа к защищённым маршрутам
- `refresh token` — JWT для обновления сессии

Текущая реализация:
- access token кладётся в `HttpOnly` cookie `access_token`
- refresh token кладётся в `HttpOnly` cookie `refresh_token`
- middleware читает `access_token`, валидирует подпись и срок жизни, затем кладёт `user_id` в `context`

### 4. Refresh flow и управление сессиями

Маршруты:
- `POST /auth/refresh`
- `POST /auth/logout`
- `POST /auth/logout-all`

Как работает refresh:
1. сервер читает `refresh_token` из cookie
2. валидирует JWT и извлекает `user_id`
3. ищет среди активных сессий пользователя bcrypt-хеш, соответствующий этому token
4. отзывает использованный refresh token
5. создаёт новую пару токенов
6. сохраняет новую refresh-сессию в БД

Разница между logout и logout-all:
- `logout` отзывает только текущую refresh-сессию
- `logout-all` отзывает все refresh-сессии пользователя

Это важное отличие: раньше оба сценария были одинаковыми, сейчас они разведены корректно.

### 5. Password reset

Маршруты:
- `POST /auth/forgot-password`
- `POST /auth/reset-password`

Как реализовано:
- создаётся случайный одноразовый `reset token`
- в БД хранится только bcrypt-хеш reset token и срок действия
- при подтверждении reset token ищется по совпадению хеша
- пароль меняется на новый, reset token очищается
- все refresh-сессии пользователя инвалидируются

Учебная особенность текущей версии:
- reset token возвращается в JSON-ответе, а не отправляется по email

Для защиты это нормально объясняется как упрощённый лабораторный сценарий без почтового сервиса.

### 6. OAuth 2.0 через Yandex

Маршруты:
- `GET /auth/oauth/yandex`
- `GET /auth/oauth/yandex/callback`

Сценарий:
1. генерируется `state`
2. пользователь редиректится на Yandex
3. callback получает `code` и `state`
4. `state` проверяется
5. код обменивается на access token Yandex
6. запрашиваются данные пользователя
7. пользователь находится или создаётся локально
8. создаются локальные JWT и refresh-сессия

Почему это соответствует ЛР 3:
- OAuth реализован вручную через HTTP-запросы
- готовые auth-frameworks не используются
- есть защита через `state`

## Безопасность

Что реализовано:
- пароль в БД хранится только в виде хеша
- для паролей используется уникальная соль
- refresh token в БД хранится не в открытом виде, а как bcrypt-хеш
- access и refresh токены передаются через `HttpOnly` cookies
- есть защита OAuth через `state`
- есть проверка владения заметкой
- есть soft delete

## Что важно честно сказать на защите

В проекте есть рабочая реализация, но не стоит утверждать больше, чем реально сделано.

Текущие ограничения:
- cookies выставляются с `HttpOnly`, но без явной настройки `SameSite` и `Secure`
- reset token возвращается в ответе API, а не отправляется по email
- сроки жизни токенов сейчас зафиксированы в коде, env-переменные `JWT_ACCESS_EXPIRATION` и `JWT_REFRESH_EXPIRATION` пока не используются
- OAuth фактически реализован только для `yandex`, хотя в примере env есть `OAUTH_PROVIDER`
- миграции сделаны через `GORM AutoMigrate`, а не через отдельные migration-файлы
- rate limiting и защита от brute force пока не реализованы

Это лучше проговорить прямо, чем заявлять несуществующую функциональность.

## Почему выбран bcrypt

Короткий ответ для защиты:
- это стандартный и проверенный способ хеширования паролей
- он медленный специально, что затрудняет brute force
- хорошо поддерживается в Go
- подходит для учебного проекта

## Почему нужны access и refresh token одновременно

- `access token` живёт мало и используется на каждом защищённом запросе
- `refresh token` живёт дольше и нужен только для обновления сессии
- если access token утечёт, окно риска меньше
- refresh token можно отозвать через серверную запись в БД

## Зачем нужен /auth/whoami

Потому что токены лежат в `HttpOnly` cookies:
- фронтенд не может прочитать cookie из JavaScript
- поэтому он спрашивает сервер: авторизован ли пользователь и кто это

## Зачем нужен параметр state в OAuth

`state` защищает от CSRF:
- перед редиректом на провайдера сервер создаёт случайное значение
- провайдер возвращает его обратно
- сервер сравнивает возвращённый `state` с сохранённым
- если значение не совпало, запрос отклоняется

## Частые вопросы преподавателя

### В чём разница между аутентификацией и авторизацией?

- Аутентификация отвечает на вопрос: кто пользователь.
- Авторизация отвечает на вопрос: что этому пользователю разрешено.

### Почему нельзя хранить пароль как есть?

Потому что при утечке БД все пароли сразу становятся известны. Хеширование сильно снижает риск.

### Почему соль должна быть уникальной?

Чтобы одинаковые пароли у разных пользователей не давали одинаковый результат в БД.

### Чем отличается logout от logout-all?

- `logout` завершает только текущую сессию
- `logout-all` завершает все сессии пользователя

### Почему refresh token хранится в БД?

Чтобы можно было:
- отзывать сессии
- отделять текущую сессию от остальных
- контролировать повторное использование токена
